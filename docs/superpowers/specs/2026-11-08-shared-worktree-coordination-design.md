# Agent Tabs: несколько агентов в одной рабочей копии — правило, защита, согласование, уборка

Дата: 2026-11-08. Статус: утверждена владельцем 2026-11-09.

## 1. Зачем

В десятках проектов параллельно работают несколько сессий агентов в одной рабочей копии. Сейчас ничто им не мешает
переключить ветку под ногами у соседа, сделать `stash`/`reset --hard`, переписать файл, который сосед правит прямо
сейчас, или наделать `git worktree` и веток и бросить их (у владельца — 37 брошенных копий одного проекта). Нужен
общий механизм для любого проекта, без договорённостей в промпте конкретного репозитория.

## 2. Что видит пользователь

1. Агенты сами не переключают ветки в общей копии и коммитят только свои файлы.
2. Если агент всё же пытается сделать что-то, что заденет соседа, команда не выполняется сразу: соседям приходит
   запрос, они отвечают, и команда либо проходит, либо агент получает причину отказа и меняет план. Человека зовут
   только когда соседи не отвечают на действие, которое может уничтожить их работу.
3. Файл, который правит одна сессия, другая не перепишет молча: она узнаёт «занят сессией „…“ до 14:20».
4. В «Безопасности» (или отдельном разделе) — «Рабочие копии и ветки агентов» по каждому репозиторию: что создали
   агенты, что уже влито; влитое убирается одной кнопкой или само через N дней.

## 3. Части

### 3.1 Правило в системном промпте (дёшево, сразу везде)
В правило автономии, которое плагин передаёт хосту (`--append-system-prompt`), добавить: в общей рабочей копии не
переключать ветки, не делать `stash`/`reset --hard`/`rebase`; коммитить только свои пути (`git commit -- <пути>`);
для изолированной работы просить изоляцию OmO, а не делать `worktree` самому. Просьба, не гарантия.

### 3.2 Защита знает про соседей (гарантия)
Служба защиты уже видит каждый вызов. Добавляется знание «кто ещё работает в этой рабочей копии» — корень
репозитория (`git rev-parse --show-toplevel` от cwd вызова) и живые сессии с тем же корнем (плагин сообщает их службе;
сессия жива, пока у неё есть хост и её последний вызов был не позже N минут назад).

- **Действия над всей копией** (`git switch/checkout <ветка>`, `checkout -- .`, `stash`, `reset --hard`, `rebase`,
  `clean`, `worktree remove`): при живых соседях не выполняются сразу, а становятся предложением (3.3).
- **Аренда файлов.** Запись в файл (инструменты правки и распознанные записи из bash) берёт аренду на 15 минут,
  каждая правка продлевает. Запись в файл, арендованный другой живой сессией, получает ответ «файл правит сессия
  „…“ до HH:MM — подожди, возьми другое или попроси через `coordinate`». Аренда снимается, когда сессия закоммитила
  файл, закончила ход без открытой работы или умерла.

### 3.3 Согласование — согласие затронутых, не голосование
- **Кто затронут:** для действия над копией — все живые соседи по копии; для файла — арендатор.
- **Запрос:** каждому затронутому приходит сообщение в его сессию: кто, что, зачем, id предложения, как ответить.
- **Ответ — инструмент `coordinate`** (расширение OmO из кита, говорит со службой защиты через хук-сокет):
  `agree`, `object` с причиной, `wait` с минутами (≤ 30), `release` (для аренды — отпустить файл); у инициатора —
  `request` (попросить файл), `status` (что с его предложением).
- **Развязка:**
  - все затронутые `agree`, либо им нечего терять (простаивают и у них нет незакоммиченных изменений в задетых
    файлах) → команда проходит, инициатор получает «согласовано»;
  - любое `object` → инициатор получает причину, команда не выполняется;
  - `wait` → предложение повторяется после срока само;
  - кто-то молчит 2 минуты: для аренды файла — инициатор ждёт; для действия над копией — вопрос человеку (ночью —
    в «Отложенные»). Молчание согласием не считается.
- Большинство не решает ничего: одно возражение затронутого весит больше любого числа согласий.

### 3.3a Имена и передача задачи хозяину файла (как `task_send`)
- **Имя агента** — заголовок сессии и короткий id (`«Выкладка LB29» · a1b2`). `coordinate who` показывает агенту соседей по копии: имя, что
  делает сейчас, какие файлы арендует; то же видит человек во вкладке.
- **`coordinate handoff <файл> <что сделать>`** — вместо ожидания: служба находит арендатора, плагин вставляет запрос
  в его идущий ход (`steer`; если он простаивает — `prompt`), тем же путём, как `task_send` доставляет сообщение
  дочернему агенту. Инициатор не ждёт и продолжает своё.
- Хозяин файла отвечает `coordinate accept <id>` (сделал; можно с коротким итогом) или `decline <id> <причина>`;
  ответ приходит инициатору таким же сообщением. Нет ответа 15 минут — инициатор получает «без
  ответа» и решает сам (подождать аренду или взять другое); человека не зовут.
- Одна доставка для всего: запросы согласования (3.3), передача задачи и ответы идут одним путём с устойчивым
  `clientMessageId` (как очередь «Отложенных»): повтор не доставляет дважды.
- **Внутри команды OmO** (`team_create`) своя почта уже есть (`task_send` по имени участника): `coordinate`
  её не дублирует, а только видит участников как соседей (аренды, действия над копией). Между независимыми
  вкладками — `coordinate`.
- Готовые решения для сравнения: MCP Agent Mail (имена, почта, треды, добровольные аренды; агент
  читает почту сам), Agent Teams Claude Code (команда внутри одной ведущей сессии). Отличие здесь —
  доставка в идущий ход и принуждение защитой.

### 3.4 Уборка рабочих копий и веток
- Раздел по каждому репозиторию: `git worktree list` и ветки, созданные агентами (по имени/автору коммитов/записи
  о создании), с пометками «влита в основную», «есть невлитые коммиты», «грязная копия».
- «Убрать влитое» — `worktree remove` + `branch -d` только для влитых и чистых; невлитое и грязное — только вручную.
- Изоляция OmO (копия во временной папке, патч назад, удаление копии) — основной путь для параллельной работы в
  одних файлах; самодельные `worktree` в папке проекта песочница по-прежнему не даёт создать.

## 4. Не цели
- Слияние правок двух агентов в одном файле (merge), блокировки на уровне строк.
- Согласование между разными средами (OmO с разными папками агента).
- Распределённые копии одного репозитория на разных машинах.

## 5. Анти-цели
- Команда, уничтожающая чужую незакоммиченную работу, проходит без согласия хозяина этой работы или человека.
- Агенты зависают в ожидании друг друга навсегда (у каждого ожидания есть срок).
- Уборка удаляет невлитую ветку или грязную копию.
- Механизм мешает одиночной сессии: без соседей всё работает как сейчас.

## 6. Проверить первым делом
- Может ли расширение OmO зарегистрировать инструмент и как ему говорить с хук-сокетом из песочницы.
- Как надёжно понять «сессия жива и в этой копии» (хост, `list_sessions`, время последнего вызова).
- Как модели реагируют на запрос соседа и на «файл занят» — живьём, двумя сессиями на одном репозитории.

## 7. Замеры

### Решение C1 (владелец, 2026-11-09)

- P44 сохраняется: координация гарантируется, только пока служба отвечает. При недоступности, обрыве или
  некорректном ответе хук решает локально, как раньше; сбой инфраструктуры не является свидетельством опасности
  команды. Службу поддерживает launchd. Одиночная сессия не должна менять поведение из-за этого механизма.
- Через службу проходят инструменты записи, распознанные записи из bash и действия git над всей копией.
  Чтение и остальные локально безопасные вызовы сохраняют быстрый путь. Бюджеты подключения и ответа не меняются.
- Источник соседей — собственные записи службы о вызовах: durable `session_id`, корень репозитория через
  `git rev-parse --show-toplevel` (с кэшем по cwd) и время последнего пришедшего вызова. Сессия жива 10 минут.
  Это уточняет §3.2: наличие хоста и `sessionsList` плагина в фазе 1 не используются; ошибка опроса не означает
  отсутствия соседей. Локально пропущенные чтения не обновляют эту отметку.
- Аренда длится 15 минут от последней разрешённой записи; снимается после коммита файла, истечения срока
  или потери активности сессии. Надёжного сигнала «ход окончен без открытой работы» у PreToolUse нет,
  поэтому это освобождение в фазе 1 не требуется. Явное закрытие сессии плагином — интерфейс будущей фазы.

### 7.2 Что известно о живых соседях

Хук передаёт `session_id` (durable UUID, не RPC handle), `cwd`, имя инструмента и его вход. Этого хватает
для принятого C1: служба разрешает канонический корень через Git, кэширует его по каталогу, хранит время
пришедшего вызова и считает сессию живой 10 минут. Вложенные cwd и симлинки сведены к одному пространству аренды.
Корни разных рабочих копий не объединяются по общему Git-репозиторию.

Плагин дополнительно знает соединение с хостом, открытые сессии и `list_sessions` с cwd, durable id и статусами
(`src/daemon.ts`, `src/panel/sessionsList.ts`). Но `fetchLiveSessions` возвращает пустой массив и при ошибке RPC:
это не доказательство отсутствия соседей. Эти сведения не используются как источник истины фазы 1.
Локальные чтения обходят службу и не продлевают активность; длинный ход без приходящих вызовов после 10 минут
перестаёт считаться живым. Это осознанная граница C1, а не обнаружение смерти процесса.

Аренды хранятся только в службе: 15 минут от разрешённой записи. После изменения HEAD на следующем пришедшем
вызове служба проверяет историю конкретного файла и его чистоту. Коммит другого файла, неудавшийся коммит
или новые незакоммиченные правки аренду не снимают. Истечение аренды и активности также обрабатывается
при обращении; после рестарта служба начинает с пустым состоянием, согласно границе доступности C1.

### 7.4 Место подключения фазы 2

`startService` создаёт один `Coordination` (`kit/guard/coordination.mjs`). Он владеет `roots`, `sessions`
и `leases`; `prepare` разрешает корни и актуализирует состояние, `conflict` проверяет занятие,
`reserve` синхронно проверяет и резервирует все пути без частичного захвата.
Один и тот же объект обслуживает немедленные решения и повторную проверку после ответа человека.
Запросы для всей копии учитывают состав соседей в ключе; новый сосед требует нового согласования,
а whitelist и ответ модели не заменяют решение человека. При отсутствии ответа действует существующий deferred.

В фазе 2 новые операции hook-протокола `coordinate` должны обращаться к этому экземпляру,
а не заводить отдельный реестр. Доверенный плагин сможет дополнять durable id заголовком и доставлять
запросы через steer/prompt. Явное закрытие сессии должно удалять её записи и аренды через admin-протокол;
`release`/handoff должны проверять владельца в том же реестре, а передача аренды выполняться атомарно.
Фаза 1 не добавляет эти операции, доставку сообщений или голосование.

Открытые вопросы фазы 2: как связать подтверждённое завершение без открытой работы с durable id; как проверять
личность ответившей сессии и доставлять запрос повторно без дубля; как показывать заголовки соседей вместо UUID.
Граница P44, TTL активности и отсутствие обязательного turn-end в фазе 1 уже решены C1.

## 8. Решения этапа 2

### 8.1 Доставка: служба отвечает за единственную очередь

`kit/guard/coordinationHost.mjs` соединяется с host socket текущего окружения, проверяет HMAC
хоста по launch key и аутентифицируется. `list_sessions` находит durable id и путь журнала;
`open_session {sessionPath, retain_on_disconnect:true}` временно подключает адресата.
Его идентичность проверяется по **`open_session.state.sessionId`**. Верхний `sessionId` — только
RPC handle. Live-прогон обнаружил неверное предположение исходного транспорта о верхнем
`durableSessionId`; реалистичная фикстура сначала дала два отказа, исправление — четыре проходящих теста.

Доставка использует `steer {whenIdle:"start", clientMessageId}`: хост атомарно запускает
свободную сессию или ставит сообщение в очередь занятой. Это исключает гонку между отдельными
`get_state` и `prompt`. Подтверждением служат `started` / `queued`, затем служба отпускает
своё подключение. Открытая вкладка VS Code не требуется.

ID сообщения стабилен: `coordinate-<request>-<recipient>-<event>`. Ошибка транспорта оставляет
сообщение в очереди с тем же ID и текстом. Подтверждение приёма не означает согласие соседа.
Тест `coordinateHost.test.ts` проверяет потерю соединения после приёма, повтор с тем же ID,
доставку без вкладки, отказ при подмене адресата и неподтверждённом хосте. Повторный ID с
другим текстом host отклоняет как `client_message_id_conflict`; повторять следует исходное сообщение.
Ответ человека на coordination-карточку доставляет служба; `DeferredInbox` не создаёт вторую очередь.

### 8.2 Ответ: только из адресованной сессии

`coordinate-extension.mjs` берёт cwd и `ctx.sessionManager.getSessionId()` из runtime.
Схема инструмента не принимает caller id. `Coordination.reply` сравнивает этот durable id
со списком адресатов запроса; посторонний получает «Ответить может только адресат этого запроса».
`coordinateExtension.test.ts` проверяет передачу идентичности из контекста, `coordinate.test.ts` —
отказ постороннему, идемпотентный ответ и переходы handoff/proposal.

Handoff не передаёт аренду: владелец сам меняет файл и вызывает `accept` после выполнения.
Через 15 минут без ответа запрос завершается как `unanswered`, без обращения к человеку.
Для действия над всей копией нужны согласия всех затронутых соседей; одно возражение запрещает
действие. Молчание через две минуты передаёт вопрос человеку, `wait` назначает новый раунд,
а новый сосед требует нового согласования. Таймауты проверяются управляемыми часами.
Эта проверка связывает ответ с контекстом инструмента; криптографической аттестации отдельного
агента поверх доступного ему hook socket этап 2 не добавляет.

### 8.3 Завершение: lifecycle расширения и резервный TTL

Расширение обрабатывает `session_shutdown`: причины `quit`, `new`, `resume`, `fork`
закрывают прежнюю durable identity. `reload` сохраняет её. Отсоединение вкладки, отпускание
транспортного attachment и неудачная доставка не означают завершение сессии.
При недоступной службе или отсутствии события действует прежний **10-минутный TTL живости**.
Регистрация обновляется на `session_start`, `agent_start`, `agent_end` и `tool_call`.

`close` удаляет аренды, активность и недоставленные сообщения закрываемых запросов;
инициатор отменённого согласования получает причину. Очистка по TTL использует тот же путь.
Служба убирает связанные pending/deferred-карточки и завершает их ожидания. Три новых теста
сначала воспроизвели утечки, после исправления проверки shutdown, TTL и карточек проходят.
Закрытие процесса без lifecycle-события может удерживать состояние до TTL — это явная резервная граница.

### 8.4 Имена и поверхность для человека

Источник названия — `ctx.sessionManager.getSessionName()`, обновляемый runtime, в том числе
через `set_session_name`. Формат — `название (первые 8 знаков durable id)`; пока названия нет,
показывается короткий id. В итоговом live-handoff наблюдались «Проверка (01a1bffe)» и
«Хранилище (01a1bffe)». Полные session UUID остаются в служебных данных, а текстовый ответ
инструмента и подписи используют имена. UUID самого запроса сохраняется для команд ответа.

`GuardAdmin` подписывается на coordination snapshot по явному флагу. `GuardApprovals` направляет
тихую строку только вкладкам инициатора/адресатов и их владельцев, восстанавливает её после
перезагрузки webview и очищает при завершении. Строка не блокирует ввод.
Существующая карточка «Отложенные» показывает название, команду и причину обращения к человеку.
Проверены маршрутизация между окнами, отсутствие строки у посторонней вкладки, восстановление,
очистка, разбор протокола, пояснение в карточке и отсутствие двойного уведомления.

Стенд `node scripts/harness.mjs` просмотрен в WebKit: тёмная и светлая темы, ширины 390 и

ввода, карточка и действия читаются. Снимки: `.agent/tasks/coordination-2/ui-{dark,light}-{390,1440}.png`.
